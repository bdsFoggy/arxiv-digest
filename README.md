# arXiv 日报故障修复包

本包基于你上传的 Python 代码和 2026-09-13 运行日志制作。已完成本地故障模拟验证，尚未安装到 bdsFoggy/arxiv-digest，也没有进行真实邮件发送。服务端为何拒绝该请求仍需 arXiv 确认，不能把代码修复等同于解除限流。

## 已查明的事实

- 原脚本包含 115 个关键词、7 个主题、6 个 arXiv 分类，按每批 6 个关键词分成 22 批。正常情况至少发出 22 次查询。
- 原脚本使用 HTTPS、带联系方式的 User-Agent、单连接，请求起始间隔至少 10 秒。官方公开上限为每 3 秒最多 1 个请求，且所有受同一用户控制的机器合并计算。这份代码本身没有显示超出该公开上限。
- 你提供的运行记录从第一个请求起即返回 429，两批各尝试 4 次，8 次全部失败。代码主动等待总计 2160 秒，即 36 分钟，然后停止检索，发送 0 篇论文的不完整通知并正常退出。
- 本次另一个执行环境的一次轻量请求也返回 429。请求只查询 physics.optics 的 1 条记录，耗时约 15.39 秒，响应正文为 `Rate exceeded.`。这削弱了“只有你这条复杂查询有问题”的解释，但不能排除两个环境都受某种服务端策略影响。
- 该实测响应没有 Retry-After；Server 为 Google Frontend，X-Cache 为 MISS, MISS, MISS。它不足以证明限流按哪个 IP、网段、客户端、后端配额或全局负载计算，也不能仅据这些头部断言 GitHub 被封。
- 官方状态页在调查时显示 export.arxiv.org 正常，没有提供能解释这次拒绝的公告。状态页正常不代表每个 API 请求都可用。

实测请求发生于 2026-09-13 07:32 UTC。诊断详情在本包 `observed-response.json`。这是本次调查环境的响应，不是从你 GitHub 日志中恢复的响应头。

## 本包解决的问题

| 原问题 | 修改后的行为 |
|---|---|
| 每个关键词批次单独等待 18 分钟 | 首次遇到 429 或 403 就暂停整个任务，不再请求下一批 |
| 冷却时间随 runner 退出丢失 | 默认至少冷却 1 小时；若 Retry-After 更长则遵守，并跨次保存 |
| 每次重跑都从第一批开始 | 保存完成批次，恢复时复用结果，不重复请求已完成批次 |
| 连续失败后遗漏两天以前的论文 | 保留上次完整检索起点，自动扩大补查范围；首次安装补查 7 天 |
| 邮件成功导致失败检索也显示绿色 | 检索未完成返回非零状态，即使通知邮件发送成功也显示失败 |
| 日志到最后才一次性出现 | Python 使用 `-u` 并实时打印时间戳 |
| 原日志没有服务端定位依据 | 保存失败响应头、有限正文、查询 URL、GitHub run ID 和代码 SHA |
| 手动与定时任务可能重叠 | 同一个 concurrency group 串行执行；不中断正在保存进度的任务 |
| 原代码达到分页上限也可能当作完成 | 显式报告不完整，不推进覆盖时间 |
| 网络错误或无效返回被当成没有论文 | 校验 Atom、日期顺序和 totalResults；异常不会冒充空结果 |

保留原关键词、分类、收件人、主题组织、去重及旧论文新版更新识别。没有添加 `submittedDate` 两天过滤，因为它会漏掉首次提交较早但最近更新的论文。

正常无故障时仍是至少 22 批请求，不承诺一定比原来 6 分钟更快。减少的是失败恢复时的重复请求和重复长等待。正常网络请求使用约 10 分钟的调度预算，工作流另设 12 分钟抓取步骤上限，留出保存进度的时间。底层 socket timeout 不是精确的整个响应墙钟上限，因此不能声称每次请求绝对在 45 秒内结束。

## 安装到现有仓库

1. 用本包的 `arxiv_daily_digest_simple.py` 替换仓库同名脚本。
2. 在仓库根目录添加 `state_store.py`，并添加或合并 `requirements.txt` 中的 feedparser 版本固定项。
3. 用本包 `.github/workflows/arxiv.yml` 直接替换仓库同路径文件，不要另外添加第二份日报工作流。已通过公开 GitHub API 核对 main 提交 04aab66d72057a93bcc309208713e9308594cc1d，脚本与上传版逐行一致。原工作流包含无分支限制的 push 触发且没有 concurrency；修复版去掉 push 触发并串行执行。原 cron 为 22:30 UTC，即新加坡 06:30；本包采用前述修复安排，改为 08:07 并增加恢复检查。实际工作流尚未替换。
4. 保留已有 `SENDER_EMAIL`、`SENDER_PASSWORD` Secrets。工作流需要 `contents: write`，以将恢复进度保存到专用的 `arxiv-digest-state` 分支。如果仓库组织策略禁止该权限，状态保存会明确失败，需要先解决该配置；不会悄悄退回无状态运行。
5. 在 Actions 手动运行日报，mode 选 `resume`。初次会建立恢复分支并补查最近 7 天，论文数可能高于平时。这个分支存放论文元数据、待补查范围和冷却时间，不保存密码或 token。首次创建以当前代码提交为基点，因此也会包含代码快照。

提供的时间安排按新加坡时间计算。

| 时间 | 用途 |
|---|---|
| 08:07 | 每日正常运行 |
| 10:17、14:27、20:37 | 恢复检查；当天已完成就直接退出，不请求 arXiv、不重复发日报 |

GitHub 定时触发可能延迟，时间不是准点保证。若恢复的是前一天的未完成周期，会先发送补查结果，再由下一次恢复检查抓取当前周期。程序保留两天重叠窗口以缓冲索引延迟，不能保证覆盖超过该窗口的未公布索引延迟。

## 判断修复是否生效

- 正常时应看到 `COMPLETE`，预览中包含实际查询范围。
- 发生 429 时只会发出这一次失败请求，输出 `INCOMPLETE`，并保留待补查批次。等待后续计划运行，不要短时间连续手动重跑。
- 冷却期间再启动应输出 cooldown，且不请求 arXiv。
- 下次恢复应出现 `Reuse completed batch`，表明已完成查询没有重跑。
- 每个新加坡日最多发送一次不完整检索通知；恢复成功后再发送完整日报。SMTP 失败不推进交付时间。SMTP 与 GitHub 状态写入不能构成原子事务，邮件发出后进程意外结束或状态保存失败时，下一次可能重复发送，不声称严格 exactly-once。
- 运行页面的 Artifacts 包含 `arxiv-diagnostics-…`。内部有 `http-diagnostics.jsonl`、`status.txt`、日报预览以及恢复状态备份。
- 专用分支保存进度失败时 workflow 会报错；Artifacts 中保留可恢复副本。不要删除进度分支。手工删除或改坏状态会破坏补查连续性。

## 如果仍从第一条请求开始返回 429

这表示服务端拒绝仍然存在。应将时间、查询 URL、运行记录和响应诊断交给 arXiv 支持，请他们确认具体触发规则。可在 Actions 手动运行 mode `diagnose`，它使用原来第一批关键词的查询，遵守已存冷却时间，不发送邮件；429 只请求一次，5xx 或传输错误允许一次短重试。不要在冷却期间换 IP、换主机或加随机参数试图绕过限制。

本包 `support-request.txt` 是已经准备好的英文问题描述，尚未发送。收到服务端解释后，才能确定是否需要修正某类查询、调整运行安排，或申请纠正误限流。

没有直接把日报改成 RSS。官方 RSS 每日更新，组合 feed 上限 2000 条；单独换 RSS 不能证明已保留原来“最近两天首次发布或更新”的覆盖，也不能自动补回中断期间的全部历史内容。需要单独设计、验证补查路径后才能替换。
